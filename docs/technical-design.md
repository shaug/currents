# Currents technical design

**Status:** Production design for implementation planning, revised after comparative evaluation and integration spikes. Contracts are requirements, not claims of implemented or production-qualified software.  
**Date:** 2026-11-09 UTC  
**Authority:** [Architectural constitution](constitution.md), including its read-only institutional-access clarification.

## 1. Purpose and scope

Currents represents the household's financial position now, explains the evidence behind it, and projects conditional futures. The durable record and its meaning survive any client. This document specifies architecture, semantics, contracts, security, and acceptance criteria. Its companion implementation plan defines sequencing and tickets. Neither document authorizes live account access, payments, remote deployment, credential generation, or application implementation by itself.

The constitution governs where earlier conversation proposals differ. Explicit owner requirements add important scope:

- The first usable release covers spending, cash, cards, debt, investments, manual assets/liabilities, net worth, and Apple Card. It is not a spending-only release.
- Native macOS is the primary experience. A mobile component supports Apple Card acquisition. CLI and restricted agent clients share the engine; they do not duplicate financial semantics.
- Reliable downloads, reconciliation, suspicious-activity review, historical trends, merchant normalization, categories, tags, and annotations are required. Budgeting tools are not required.
- Account-level forecasting over one, three, and twelve months is MVP scope. Accurate present state takes priority; forecasts are nonauthoritative.
- The product works without AI. Plaid is an acceptable candidate, not a selected provider or permission to share data. Public code does not mean public financial state.

A usable release includes every account in an explicit inventory, even when its value or history is unknown. Manual/file paths are mandatory. They do not silently satisfy a requirement for reliable automatic acquisition. Apple Card automation is a named feasibility gate in section 13, not an assumed capability.

Excluded: institution-side payments, transfers, trades, account changes, tax filing, tax-lot optimization, comprehensive accrual accounting, budgeting envelopes, multi-tenant hosting, concurrent cross-device ledger editing, and a general plugin marketplace. Reviewing suspected fraud does not dispute a charge with an institution. Recording a transfer describes activity; it never executes it.

## 2. Architecture decisions

These are author-selected technical proposals. Changes require revising this design and its compatibility obligations, not leaving the implementation to choose competing semantics.

| Decision | Choice and rationale |
|---|---|
| Engine and clients | Rust workspace owns domain, replay, queries, and planning. Pin doubleentry v0.9.0 at upstream commit `3c514c97169a98d96f0668e6addfd92e1e8f6f69` behind a private accounting adapter and narrow maintained SQLite composition seam. Swift 6/SwiftUI with AppKit is the Mac client. Rust financial logic has no UI, Keychain, FinanceKit, network, or ambient wall-clock dependency. |
| Runtime | One per-user, on-demand Mac owner process, `currentsd`, serializes each dataset. A thin Swift platform host owns XPC, Keychain and owner approval, and embeds the Rust service through a bounded C ABI. Mac app, CLI and restricted MCP bridge use versioned XPC messages. No TCP listener in the initial release. A Rust headless verifier reconstructs portable archives independently on macOS and Linux. The Rust service remains host-independent so a later single-owner server can use the same semantics; remote deployment is not required for the initial release. |
| Storage | One SQLCipher 4 database, including chunked evidence BLOBs, accessed through the SQLx 0.9 stack used by doubleentry. One transaction covers published evidence/domain decisions, native journal consequences, command result, and invalidations. Production must first qualify a single SQLCipher-linked SQLite implementation with the seam; the spike used stock SQLite and did not prove encryption compatibility. No silent downgrade to plaintext or two-database outbox. |
| Authority and order | One append-only commit sequence per dataset. Each commit contains ordered evidence receipts and/or domain decisions. All queries pin one sequence plus semantic versions. No independent streams whose relative visibility must be guessed. |
| Numbers | Checked Rust `i128` integer coefficients with explicit decimal scale and unit. No binary floating-point in accounting, valuation, or forecast calculation. Section 5 fixes rounding and overflow behavior. |
| Corrections | Append reversal and replacement, in one commit, referencing the active recognition being replaced. Do not use arbitrary deltas for ordinary corrections. Organizational revisions have no journal effect unless an accounting mapping changes. |
| Automation | Manual adoption is the default. Explicitly enabled, versioned deterministic rules may adopt only their allowed operation types. AI and statistical matching produce proposals only. |
| Planning | Shared, portable planning module with its own durable records in the same history. It cannot issue accounting recognition commands. |
| Mobile | Narrow iOS acquisition satellite. It sends encrypted evidence bundles to the Mac through an owner-initiated file handoff; no second authoritative journal, cloud synchronization, or mobile accounting edits in this release. |
| Recovery | Encrypted full-fidelity portable archive, documented canonical records, and independent headless verification. Credentials are excluded. Section 11 fixes backup and recovery behavior. |

### Approaches and decision evidence

1. **Selected: Rust + doubleentry + private transaction seam.** The comparative evaluation reproduced native exact balancing, idempotency, atomic rejection, layered pending/settled behavior, audit, and historical views. The second spike proved a narrow same-transaction integration with Currents records, including actual COMMIT failure, process kills and lost acknowledgment. This reuses accounting validation rather than rebuilding it. The seam is a maintenance obligation, not an unmodified upstream feature.
2. **Unchanged doubleentry + durable outbox:** feasible and explicitly tested, but two files cannot provide a single atomic commit. It requires frozen validated input, separate authoritative/projected heads, ordered retries and repair. Rejected for this production baseline because that complexity is avoidable. Reconsider only through an ADR and revised read/recovery contracts if the seam cannot be maintained.
3. **Custom Store/core or embedded text-ledger engine:** a complete custom Store owns more durability code than the narrow seam; a new core reinvents validated arithmetic/history. Ledger and Beancount provide useful lot, valuation and reporting precedents but do not supply Currents' authoritative evidence/domain service. Zhang supplies Rust components worth studying, but the pinned evaluation reproduced currency-validation, error-state and booking-mode defects. No candidate replaces the Currents domain.

The earlier Swift-only proposal reduced binding cost, but it predates the demonstrated Rust embedding and storage evidence and is superseded. A general distributed event service, multi-tenant SaaS, database cluster, message bus and plugin platform are unnecessary. Upstreaming the seam is optional; production may maintain a minimal pinned adaptation with preserved licenses, a patch manifest, regression tests and explicit upgrade review. Never modify canonical history/validation to camouflage missing Currents semantics.

Spikes qualify feasibility only. The safer FFI harness was memory-only; the persistent SwiftUI demo used an older prototype bridge. Their combination, SQLCipher, shipping authentication, loss-of-device recovery, and realistic performance remain release gates. SIGKILL is process-crash evidence, not proof of physical power-loss or arbitrary I/O fault tolerance.

### Responsibility boundaries

- **Acquisition adapters:** Read allowed source endpoints; preserve sanitized source evidence, parser identity, receipts, coverage, and checkpoints. No recognition or institutional financial mutation methods.
- **Domain engine:** Account identity, evidence references, economic relationships, recognition/corrections, reconciliation, organizational meaning, capabilities, and invariant validation.
- **Journal projector:** Replay recorded complete posting instructions. No inference, current policy evaluation, network, or price lookup.
- **Query engine:** Present position, historical views, explanation graphs, coverage, review queues, and reconciliation evaluation from a pinned read basis.
- **Planning module:** Commitments, schedules, occurrence matching, scenarios, and immutable saved forecast runs. Actuals are read-only inputs.
- **Owner/storage boundary:** Key custody, serialization, transactions, local client authentication, encrypted import/export, backup, migration, and projection health.
- **Clients:** Native interaction or command translation. Window geometry and unsaved filters may be client-local. Saved categories, rules, scenarios, review decisions, and commitments are portable domain data.

The public format and headless reader are the portability guarantee. Linux core/CLI verification is required; a Linux GUI, production hosted service and simultaneous writable clients on different machines are not initial-release requirements. Native integration must not place essential financial logic in view models or platform-only storage objects.

## 3. Record model and temporal meaning

### Authoritative records

| Record | Required meaning |
|---|---|
| Dataset | Stable UUID, format versions, household timezone, reporting currency, unit catalog, ownership perimeter, commit head, and policy versions. |
| Account/component | Stable internal identity, asset/liability/income/expense/equity class, unit, normal sign, institution/source aliases, household ownership fraction, coverage intervals, and optional opening boundary. Brokerage cash, holdings, and reported total are explicitly overlapping components. |
| Import receipt | Source/connection/device identity, adapter/parser version, request and reported coverage, received time, result, cursor, truncation/completeness flags, and content references. |
| Observation version | Source identity and original IDs, sanitized source bytes or lossless source representation, reported fields and temporal precision, semantic kind, version/tombstone relationships, and content digest. |
| Financial event and leg | Local economic identity and typed account movement, related evidence allocations, lifecycle/transfer/payroll relationships, unresolved residuals, and adopted interpretation. A relationship alone does not recognize money. |
| Domain decision | UUID, ordered commit/item position, type/schema version, actor and authority, command ID/digest, references, decision time, adopted result, governing policy, and correction/supersession links. |
| Recognition | Stable recognition/lineage identity; complete posting IDs, accounts, exact units/amounts, effective and posting dates, recognition kind, evidence allocation, and scope. |
| Reconciliation claim | Comparison type, scope, cutoffs, evidence and decision dependencies, matched allocations, differences/exclusions, status, and reason. |
| Organization/planning | Versioned parties, aliases, categories, tags, notes, reporting allocations, rules, review dispositions, commitments, scenarios, and saved forecast inputs/outputs. |

UUIDs and timestamps are generated at command acceptance and recorded, never regenerated during replay. Foreign keys prohibit dangling references. Domain invariants additionally validate reference kinds, allocation conservation, dataset ownership, and supersession cycles. UUIDs do not establish economic identity.

### Time and read basis

Store source-native dates/times and normalized representations together. Distinguish economic/effective date, institutional posting date, source balance/valuation as-of time, receipt time, and decision time. Date-only values stay dates; unknown timezone, precision, and time stay unknown. No fabricated midnight or automatic timezone conversion of date-only values.

A **read basis** is `{dataset_id, through_commit, effective_scope, evaluation_instant, query_semantics_version, selection_policy_version, unit_catalog_version}`. A commit publishes receipts and decisions atomically. Every referenced record must already exist in that commit or an earlier one. Thus one sequence captures both what was knowable and what had been decided; backdated evidence cannot enter an earlier read basis. Wall-clock “now” is resolved once by the caller and saved as an explicit query argument.

Historical queries distinguish:

1. Current interpretation of a past effective period at today's commit.
2. Interpretation of that period at a saved prior commit.
3. Institution-reported position at a source-specific as-of boundary.
4. Recognized accounting position, or movements only when its opening is unknown.

Economic-time reports and institution posting-time reconciliation are different contracts. If a required date is missing, return an unknown-date bucket and incomplete result rather than borrowing another date without a labeled policy. Saved reports and forecasts pin their basis. The engine retains versioned evaluators needed to reproduce them; unsupported versions are a visible compatibility failure.

## 4. Acquisition and identity

### Capture and publication

Adapter operations are `describeCapabilities`, `fetchChanges`, `fetchSnapshot`, and `resumeImport`. The capability manifest names read endpoints, units, account types, identifier stability, revision/deletion semantics, supported history, balance semantics, pagination, and freshness expectations. Unknown capability is recorded as unknown, never inferred from successful authentication.

Raw HTTP authentication envelopes are not evidence. The adapter removes tokens, authorization headers, cookies, and secret URL parameters before persistence. It records that sanitization occurred and which contract/version performed it; it must not claim those bytes are the untouched transport response. Financial source fields are preserved. Unexpected secret-bearing payloads are quarantined rather than routinely copied into history.

Private encrypted staging holds partially fetched pages and large files. A source batch becomes visible only after page ordering, checksums, schema limits, and references validate. Receipt publication and advancing its cursor are one database transaction. Crashes before commit expose neither; retries resume or safely repeat. Completed sub-batches of a paginated import may be visible with an explicit incomplete import interval. Completeness is asserted only when the source contract supports it and the final page/checkpoint succeeds.

Ordinary source-evidence limits are explicit: 100 MiB per imported file, 1 MiB evidence chunks, 10,000 normalized observations per commit, 1 MiB per structured message. Larger sources are chunked into linked incomplete batches, or rejected with no success marker. Parsers reject path traversal, executable content, decompression bombs, unbounded nesting, and inconsistent units. Attachments are inert; viewing requires a deliberate user action in an isolated viewer. No remote resources are fetched while displaying a source document.

### Deduplication and recognition ownership

Identical sanitized content can share stored bytes, but each fetch preserves its receipt. Source-record identity is `(connection, provider_account_id, provider_record_id)` only when the adapter guarantees that scope. Changed content creates a version. Source revision order comes from an explicit provider version/supersession relation, never receipt order: an old export imported later cannot replace a newer API record. Unorderable contradictory versions remain alternatives. Parser reruns create new immutable parse products with their own version and visibility commit; adopted decisions keep their exact original parse reference. Preserve absent, null, and explicit deletion as distinct source values. Reconnecting or changing providers requires explicit alias mapping to the stable local account. Amount/date/description similarity creates a candidate, not a deduplication key. Sources without stable IDs retain file/row identities and require duplicate review across files.

Pending, posted, revised, deleted, reversed, and refunded are distinct source facts. A deletion/tombstone never erases evidence or automatically reverses accounting. Pending-to-posted linkage is versioned; an uncertain link remains uncertain. Expiry requires an explicit source expiry/reversal, a demonstrably complete source lifecycle contract, or an attributed owner decision. Mere age or absence from an incomplete fetch makes pending activity stale/unresolved, not expired. Supported expiry remains in history rather than deleting the authorization.

Economic legs carry active recognition ownership. Independently, each parsed economic movement facet carries active source-fact allocation ownership across its source-record revision and parse lineage. Creating a new leg ID cannot spend the same source movement twice. A source-fact key identifies the provider-scoped record lineage plus typed facet (for example net cash, gross pay, withholding, retirement contribution or security quantity), not an entire receipt. Active allocations from each facet conserve its exact amount; a revised or reparsed fact requires superseding/remapping its existing allocations rather than recognizing another copy. Corroborating sources may map to the same economic leg, but are not additive amounts. Different facets may support distinct consequences only under the versioned parser's declared relationships, so a payroll statement is not wrongly limited to one net-deposit fact. Ambiguous cross-source identity stays a candidate; it does not authorize either automatic merging or automatic second recognition of a fact already owned. A recognized leg cannot be recognized again with another command ID. Quantified allocations from one leg to several relationships must conserve its exact amount and cannot overlap active recognition claims. Corroborating observations may all support one leg without multiplying its amount. When independent imports have already created duplicate legs, adoption of the duplicate relationship must atomically reverse the redundant recognition and choose the survivor. Similarity alone cannot perform that correction.

### Read-only integration and refresh

A connector binary exposes no payment/trade/transfer, balance-changing, or institutional account-management operation. Connection consent and token revocation are separate administrative workflows. The provider must grant a credential whose usable financial scope is read-only. An SDK hiding write methods is not sufficient if the credential still authorizes them. If scopes cannot satisfy this rule, that connector is disabled and file/manual acquisition remains available.

Refresh is owner-triggered on application open and by an opt-in local schedule. Baseline schedule: at most once per 24 hours per connection, honoring provider restrictions and `Retry-After`. Transient failures use bounded exponential backoff (1, 5, 30 minutes, then next scheduled attempt); authentication/permission failures require review and are not retried indefinitely. No server webhook receiver is required. A provider requiring a hosted secret or webhook service needs an explicit, separately reviewed connector deployment ADR and owner consent, not a hidden relay. That ADR may use the same single-owner Rust service without changing domain authority; it must define transport, key custody, authentication, backup and operations before enabling the provider.

Source freshness and financial as-of age are separate. Each connection has an owner-visible freshness threshold; absent one, status is “not assessed,” not fresh. Failed refresh preserves the prior record and displays its age, failure, and uncovered interval. Offline operation retains all accumulated access.

### Mobile acquisition

The iOS satellite stores only its capture queue and acquisition metadata using device-protected encrypted storage. Its FinanceKit adapter is enabled only after entitlement, account eligibility, distribution, and read-operation checks succeed. It has no local recognition authority. Owner-selected statement exports can also enter its queue.

Pairing creates a random 256-bit ingress key unique to the phone and dataset, transferred through a one-time owner-verified QR flow and stored in each device's protected key store. It is not the dataset or backup key. The phone packages evidence in the SQLCipher transfer format of section 11, with device identity, monotonically increasing batch number, previous-batch digest, source coverage, and content digests. The owner chooses the receiving Mac through a system file handoff; no remote recipient or cloud destination is implicit.

The Mac validates the bundle and source scope, commits receipts, and produces an encrypted acknowledgment of batch ID and digest. The phone retains unacknowledged evidence and may resend; the Mac deduplicates the batch. Gaps remain visible and do not advance a contiguous checkpoint. Revocation disables future imports from the pairing and deletes its ingress key, without deleting already adopted evidence. Phone loss requires pairing again and discloses any unrecoverable capture gap. There is no merge of two decision histories.

## 5. Accounting semantics

### Exact quantities and balance

Represent values as `{coefficient: signed base-10 integer string, scale: 0..18, unit_id}`; the engine uses checked Rust `i128` arithmetic. Canonical form removes trailing fractional zeros, normalizes negative zero to zero, and never uses exponent notation. Scale alignment, multiplication, division, aggregation, and negation must reject overflow. Evidence outside these limits remains preserved but cannot be recognized until supported; it cannot be rounded silently.

The versioned unit catalog defines the permitted accounting scale of each currency and the precision of each security quantity. Inputs requiring quantization are shown in a preview; adopted decisions store the rounded result, exact input, remainder, and rule. Round half to even for valuations and conversions; allocate split remainders by largest fractional remainder, tie-broken by stable component ID. Never insert a rounding line just to balance an inconsistent source transaction.

A journal entry contains at least two nonzero postings. Debits are positive, credits negative. For every currency represented in an entry, the exact sum is zero. Assets/expenses are debit-normal; liabilities/equity/income are credit-normal. Presentation transforms these signs explicitly. Zero-effect interpretation changes are domain decisions, not empty journal entries.

No functional-currency balancing is used. FX records balanced native-currency legs through currency-specific exchange-clearing accounts, with actual amounts, fee legs, and observed/implied rate provenance. USD and EUR never cancel one another. FX-clearing accounts represent conversion mechanics and are excluded from household assets. Reporting-currency valuation is a separate analytical calculation using dated explicit rate evidence; a missing rate yields unconverted components, not zero. This is not comprehensive FX gain/loss or tax accounting.

Security quantities use separate security-unit accounts and quantity-control legs in the same atomic accounting adapter, never mixed with currency balancing. The position projection derives their conserved unit movements and explicit opening/corporate-action adjustments. Monetary entries do not add shares to dollars. The MVP records known trades, cash income/fees, transfers, and quantity changes; it does not infer tax lots or unknown sale basis. Section 8 defines when a monetary accounting value is unknown.

### Recognition and unresolved amounts

Importing evidence never itself recognizes activity. A user or explicitly enabled deterministic recognition rule adopts a preview with exact consequences and evidence allocations. Rules may not silently change opening positions, settle disputed identity, erase review flags, or replace prior user decisions. Replay uses adopted consequences only.

Unknown counter-entry is a named unresolved-equity account, not an expense, income, or verified asset. Known transfer intent uses a transfer-specific clearing asset or liability. Each unresolved amount has an owner-visible reason, origin, age, and residual. Unresolved-equity balances cannot be reported as income or spending. Transfer-clearing is not automatically counted as net worth.

Examples, all synthetic:

- Posted card purchase 96: debit expense 96, credit card liability 96. Pending authorization 80 has no recognized journal consequence; it remains a domain exposure for review and forecasts. Although native pending/hold primitives were evaluated successfully, the initial product does not use them as institutional lifecycle authority or a second monetary effect. Pending-to-posted adoption removes that exposure and recognizes 96 once. A later native-hold projection requires its own contract and may not change this result.
- Unexplained deposit 3,300: debit checking 3,300, credit unresolved equity 3,300. Calling it wages requires an explicit income interpretation.
- Transfer out 1,000: debit transfer clearing 1,000, credit checking 1,000. Later receipts 600 and 400 debit destination cash and credit that clearing. Fees require their own evidence and expense line.
- Supported payroll gross 5,000: debit checking 3,300, retirement clearing 500, HSA clearing 200, and withholding 1,000; credit wages 5,000. The withholding account is explicitly owner-selected as tax expense or tax prepayment. Missing payroll detail remains unresolved; never infer gross from net.

“Internal” is relative to the effective-dated household ownership perimeter. Movements across that perimeter, including partially owned accounts, require an explicit owned-share allocation; they cannot automatically be excluded as a full household transfer. A change in beneficial ownership is separately classified or carried as an unresolved ownership effect; it does not disappear from household analysis merely because both accounts appear in the inventory.

Grouping payroll or a transfer does not force every leg onto one date. Each leg has its own posting/effective date and balanced entry through the appropriate clearing account. The user can see both the economic grouping and settlement chronology.

### Openings and incomplete history

An externally maintained position without an accepted opening has **known movements, unknown absolute balance**. Newly created internal clearing/control accounts start at an explicit recorded zero creation boundary by construction. Income/expense period totals are sums of recognized flows, not claims of an institution-held opening position. Zero is not an implicit opening. Its journal-derived absolute balance and discrepancy to an external absolute balance are unavailable, not the sum of imported movements.

An opening decision records account/component, unit, exact amount, evidence, cutoff and date precision, and the set of source activity included through that boundary. Debit/credit opening equity provides the balancing entry; it is not historic income or a fictitious purchase. Liability openings use the opposite sign. The default boundary is the end of the source's stated local calendar date, but only when the source's balance semantics support that interpretation. Otherwise the owner must supply an explicit inclusion boundary before an anchor can be adopted.

For an anchored account, `balance(t) = anchor + adopted movements after the anchor through t`, subject to known coverage. Pre-anchor observations can be organized and reviewed without entering that current segment. Extending accounting history requires one replacement-segment command: retire the active opening/segment via reversal, adopt an earlier supported opening and backfill, and prove equality at the former boundary or expose the exact residual for owner resolution. It may not subtract a residual into opening equity silently. Segment replacement closes over whole affected recognitions and their dependencies, never selected postings from a multi-account entry. Reverse each affected active recognition once and re-emit every still-valid consequence with its stable economic identity and dates, then add the approved backfill/opening changes. Preview and validate all affected accounts, including transfer counterparts; balances/consequences outside the approved correction scope must be unchanged. If that closure cannot be validated, block the replacement. Two active overlapping segments for one component are invalid. Corrections to the anchor follow the same replacement contract.

A numeric anchored balance with coverage gaps is a partial reconstruction. It remains distinguishable from a reconciled or institution-reported absolute position.

### Corrections and replay

A correction atomically appends exact reversals of the active recognition postings and replacement postings. Reversals preserve original effective/posting dates and reference original posting IDs; their decision time is new. A real refund is new economic activity at its actual date, not a historical correction. Organization attaches to stable economic leg/allocation identities, not replaceable journal posting IDs. Split/merge corrections must explicitly remap it or create a visible mapping question; they cannot drop or duplicate tags/categories. Dependent associations, allocations, claims, and planning matches are revalidated in the same commit or durably marked invalid before publication.

The engine rejects double reversal, correction of an obsolete active revision, supersession cycles, and overlapping recognition ownership. Native period seals/close commands are disabled: they would prevent legitimate backdated corrections. Reconciliation claims and saved read bases provide historical evidence without sealing economic periods. Account closure is a domain visibility/lifecycle decision, never a reason to erase or block corrective history. Undo adopts another compensating revision. Past read bases still reconstruct prior beliefs.

The projector accepts only recorded amounts, stable posting IDs, account versions, and dates. It never reruns present-day rules or models. A journal hash compares canonical ordered postings, including IDs, dates, units, and recognition links; a separate domain-state hash covers organization and planning. Equal balances alone do not prove equivalent replay.

## 6. Reconciliation and present position

### Reconciliation predicates

A claim's type determines what it proves:

- **Balance agreement:** A specific institution-reported balance and an independently anchored journal balance agree at the same supported boundary, unit, and balance semantics. Exact equality is required after an explicitly disclosed source quantization rule. An accepted unexplained difference is an exception, not reconciliation.
- **Activity coverage:** All source lines in a declared complete interval are allocated exactly once to recognized legs, all relevant recognized legs are supported or explicitly excepted, and opening plus scoped movements equals closing. Offsetting missing debit/credit lines cannot pass merely because the net difference is zero.
- **Relationship settlement:** A specific transfer/payroll relationship's evidenced allocations and residuals satisfy its stated amount/unit constraints. This says nothing about the rest of the account.
- **Holdings agreement:** Position quantities match in the same security identity and corporate-action basis at the same boundary. Matching market value alone is insufficient.

A closing balance used as the opening anchor proves that boundary was established, not independently reconciled. It cannot also serve as independent corroboration for an activity claim over missing history. Unknown opening, incomplete interval, incompatible balance types, missing date mapping, or unexplained residual produces a partial/unsupported claim with reasons.

Claims preserve exact inputs, read basis, matching allocations, comparison version, and exclusions. Lifecycle: proposed, partially_supported, confirmed_for_scope, disputed, superseded. Confirmation checks the current dependency digest. A changed relevant observation version, accounting amount/date, account mapping, coverage assertion, or relationship invalidates current applicability and adds a review requirement. Dependencies include the claim’s account/unit/date predicate, so newly added or removed backdated activity in scope triggers re-evaluation even when it was absent from the original referenced-input list. A cosmetic label change does not invalidate a balance claim. Original confirmation remains reproducible at its original basis; “reconciled” is never a permanent Boolean on an account.

### Deterministic position selection

A position response contains reported assertions, meaningful journal position or known movements, pending exposure, effective/receipt times, coverage, freshness, discrepancies, selected basis, and explanation. Unknown, stale, inferred, disputed, unmatched, and reconciled are independent facets, not one overloaded status.

For each account/component and requested meaning:

1. Restrict observations to the pinned read basis and compatible identity, unit, balance kind, and valuation boundary. Reject unknown semantics as selection candidates, while retaining them as evidence.
2. Prefer the latest source as-of boundary at or before the requested effective time, not latest download time. A date-only boundary is an interval; overlapping incomparable intervals remain ambiguous.
3. Within an equivalent boundary, apply an explicitly adopted source-priority policy, if one exists. Without it, consistent assertions can corroborate; conflicting values remain a conflict with no single selected amount. Provider identity or confidence does not silently break the tie.
4. Use that institutional assertion for the selected reported account position. Otherwise use an accepted manual assertion; otherwise an independently anchored journal balance with coverage qualification. If none is meaningful, the position is unknown. Do not roll a source assertion forward unless the engine has explicit complete coverage and inclusion/exclusion knowledge for the intervening movements.
5. Show the journal discrepancy only for comparable absolute balances. Pending/available/posted/statement balances are not subtracted as if equivalent.

A source-reported value remains authoritative about what that source asserted, even when stale or disputed. It does not automatically override another incompatible assertion, establish missing history, or trigger an adjustment.

### Household aggregation and transfer overlap

Account aliases resolve to one stable owned account. The ownership perimeter and fractional interests are explicit owner choices; unknown ownership cannot default to 100%. Use one representation of each component: brokerage total **or** its cash plus holdings, never both. Joint-account duplicates, debt embedded in asset totals, and paired transfer legs carry overlap relationships.

Every in-flight transfer has membership states relative to each selected position basis: included, excluded, or unknown, with supporting line/cutoff evidence. A source as-of timestamp alone does not prove inclusion. Add a clearing asset only when the sending balance already includes the outflow (the funds have left), the destination balance excludes the receipt, and the claim to the in-flight funds is supported. Suppress clearing already included at the destination. If the sending basis still includes the funds while the destination includes the receipt, remove the evidenced overlap from aggregation without rewriting either assertion.

When inclusion is uncertain, return a bounded aggregate range if the alternatives are finite and evidenced; otherwise return an indeterminate aggregate with component positions and the obstruction. Do not silently sum asynchronous reports into precise net worth. An unadjusted source sum may be shown only as such, never labeled net worth. Missing components, unknown ownership, missing rates, and unsupported valuations remain explicit omissions; a known subtotal is not complete net worth.

This rule addresses the case a transfer receipt is included in a destination balance before its transaction feed arrives. Journal clearing alone cannot decide whether money should be counted again.

## 7. Organization, review, and historical analysis

Merchant/counterparty identity, reporting category, tags, notes, and accounting accounts are separate concepts. Categories are not automatically chart-of-account nodes. Reporting allocations sum exactly to the signed recognized amount being categorized; categories partition that amount while tags are nonadditive selectors (matching parent and child counts a leg once); unmatched and unknown portions remain visible. Refunds can be linked to original purchases but appear on their actual effective dates by default; a separate restated-spending view must identify its alternative date basis.

Precedence for one field is explicit user override, adopted account-scoped rule, adopted dataset rule, provider proposal, then unknown. Within a rule tier, owner-assigned priority wins; equal-priority conflicting rules generate a conflict rather than arbitrary last-writer behavior. An import or rule version change never overwrites an adopted value. Bulk application previews the exact affected identities and conflicts, and writes individual traceable decisions under one command. A user may release an override with a new decision.

The review inbox includes newly received activity, changed amounts/identities, unmatched/duplicate candidates, unresolved classifications, and user-flagged suspicious activity. State is unreviewed, reviewed, flagged, or resolved with actor/time/reason. Material financial changes reopen review. “Reviewed” neither recognizes a transaction nor reconciles it, and a flag does not reverse it. The baseline offers complete review and deterministic filters (new counterparty, owner-configured amount threshold, suspected duplicate); it makes no guarantee of fraud detection and files no institutional dispute. Alerts remain local by default and omit financial details from lock-screen notifications.

Historical outputs include searchable registers, spending/income by normalized party/category, account cash flows, and monthly trends. Transfer movements appear in account cash flow but not household spending/income. Unknown and unresolved amounts receive their own buckets. Each report discloses accounting/organizational basis, effective or posting-date convention, currency conversion, included accounts, and coverage. Incomplete periods are labeled and cannot silently enter complete-period averages. No budget target or spending limit is required for these functions.

AI is an optional proposal producer. Its input fields, model/version, rule context, outputs, and adoption provenance are retained locally. Source text is data, not instructions to the model or engine. Remote AI is disabled; enabling it requires approval of the recipient and fields, a disclosed retention policy, and a separate design review. AI cannot gain recognition authority merely by returning a high confidence score.

## 8. Investments, loans, and manual positions

Security identity uses source identifiers and explicit local mappings; ticker alone is not identity. Holdings quantities, source market totals, price observations, cash, known acquisition costs, and performance history are separate. Price has currency, venue/source, timestamp/precision, and corporate-action basis. Never multiply a pre-split price by a post-split quantity. If quantity and price cannot be placed on a compatible basis, show source-reported market value or unknown valuation rather than manufacture it.

Quantity changes use adopted evidence-backed movements or explicit quantity opening/adjustment decisions. Trade cash and quantity consequences commit atomically when both are known; a missing side remains explicit. A reinvested dividend is a linked income-plus-purchase pair, not an extra cash deposit on top of that pair. A split changes quantity basis, not income. An incomplete holdings snapshot is not permission to delete missing securities. Quantity openings/backfill obey the same unknown-baseline and nonoverlap rules as cash. Snapshot completeness and account/subaccount scope determine whether absence is meaningful. Transfers preserve security identity without inventing a purchase.

Known purchases record investment carrying amount and cash effects. A sale with unknown cost basis records cash against a specifically labeled disposal-clearing account and a separate supported quantity decrease. It does not invent gain or derecognized cost. Affected carrying-value and return reports become unavailable or partial until basis is established; the balanced journal's raw investment-account sum is not a supported current asset valuation. Disposal clearing is excluded from income and present net worth. Known dividends/interest and fees can be recognized independently. Market changes remain analytical valuations, not synthetic trades or automatic income.

The MVP shows holdings, allocation by known value, contribution/withdrawal cash flow, and source value history. It does not claim cost-basis return, time-weighted return, or tax gains when the necessary complete history is absent. Sophisticated tax-lot reconstruction is outside scope, rather than an unnamed future dependency of current position.

Loans separate principal, accrued/charged interest, fees, and reported payoff/statement balances. A payment's unknown decomposition uses a disclosed unresolved allocation; it cannot all be assumed principal. Amortization predictions are planning assumptions, not actual principal changes. Manual property/assets/liabilities use dated owner observations with method and ownership share, not invented monthly appreciation. Staleness is visible; a saved value never refreshes merely because the app opens.

## 9. Forecast semantics

### Portable inputs and calendar

A commitment defines stable identity/version, nominal amount or explicit low/base/high values, account legs, intended due date, settlement-date rule or range, recurrence, timezone, start/end, exceptions, and provenance. Commitments may be expense, income, transfer, card purchase, card payment, or debt payment. Paired transfers share one occurrence identity; receipt can settle after outflow. Durable confirmed future commitments belong to the planning history, never the journal.

Use the proleptic Gregorian calendar and the dataset's owner-confirmed IANA timezone. Daily, weekly, monthly, and annual recurrences have an integer interval. Monthly days beyond month end clamp to the last day; “last day” is a distinct rule. Annual February 29 clamps to February 28 in nonleap years. Dates have no invented time of day. Default settlement equals due date with **no weekend/holiday shift**. A commitment can select next/previous weekday or an explicitly supplied versioned holiday calendar. A client may not silently apply its own banking calendar.

One, three, and twelve **calendar-month** horizons run from a saved starting date to the clamped corresponding ending date, with daily buckets and inclusive end date. Each occurrence has stable logical identity `(commitment_id, series_generation, ordinal)` and a separate version. Editing amounts/dates preserves occurrence identity; a recurrence-pattern change explicitly supersedes/remaps affected future occurrences and their matches. It cannot leave old and new expectations simultaneously active. All inputs, expanded occurrences, exceptions, timezone/calendar data, algorithm version, and outputs are stored for a saved run. This permits exact output comparison even if later timezone databases change.

### Starting balances and occurrence consumption

Forecasts are per account. Select a posted/ledger balance at a known boundary or a supported anchored journal balance, using section 6. Available balances are not a default because they may already include holds. A user may explicitly choose another starting basis only with its known inclusion map. If pending inclusion is unknown, return alternative starting scenarios or unavailable output, not an unexplained point estimate.

For every actual or pending leg, track whether it is already included in the starting amount, lies after the starting boundary, and matches an expected occurrence. An included actual reduces the remaining expectation but is not applied again. An actual after the boundary is applied once and consumes its matched expectation. An unmatched actual is applied once, independently of proposed matches. Pending exposure consumes a matched expectation provisionally, with the pending and hypothetical event represented as alternatives rather than additive debits. Uncertain candidate matches are review items; they do not silently consume expectations.

Planning allocation identity is `(occurrence_id, planned_leg_id, economic_leg_id, allocation_version)`. Residuals are computed per planned leg, never across both sides of a transfer. The actual sending leg of a 1,000 transfer can satisfy its sending expectation while the full receiving expectation remains open. Across active matches, allocated amounts cannot exceed the actual economic leg or consume it for several unrelated expectations; explicit partial allocations conserve its amount.

An accepted pending-to-posted lifecycle link replaces the provisional pending exposure/allocation with the posted economic leg, using the posted amount and rechecking starting-balance inclusion. Pending 80 followed by posted 96 contributes 96 once, not 176; if that 96 is already in the starting balance it is not applied again. Preserve the replaced planning interpretation and prior saved forecasts. Supported pending expiry releases its provisional match but does not cancel the underlying commitment. Uncertain lifecycle linkage produces explicit alternatives/unresolved overlap, not a confident additive exposure.

For a fixed-amount planned leg, residual expected amount is expected minus its accepted actual/pending allocations in the same unit, never below zero. Overpayment becomes an explicit variance. Variable occurrences require owner-approved revised amount/range or remain partly matched; a partial payment cannot arbitrarily close them. Cancellation/skipping is a planning decision. Overdue unsatisfied occurrences remain visible, but are not repeatedly posted daily or turned into actuals. They affect a new run only through an explicit carried-forward due-date assumption.

Card purchases increase forecast card liability and spending; card payments decrease bank cash and card liability, without spending again. Statement-balance or fixed-amount payment rules use the same explicit occurrence/actual model and source statement boundary. Never assume a credit limit is cash or assume that all card spending will be paid in full. Loan-payment splits use supplied planning assumptions and expose unknown principal effects.

### Estimation and scenarios

Baseline forecasts use accepted commitments and accepted variable-spending assumptions. Recurrence detection groups adopted, nonduplicate legs by account, normalized counterparty, direction, unit, and financial kind, using one explicit effective-date basis (or one labeled posting-date basis when effective dates are absent). Examine the latest six legs, requiring at least three and no more than one leg per candidate period. Candidate cadences are weekly, fortnightly, monthly, quarterly, and annually. Every adjacent occurrence must fit its cadence within two calendar days for weekly/fortnightly or three days for calendar-month/year rules, including last-day clamping. Missing periods are shown as exceptions, not silently filled. Choose the cadence with the smallest total absolute date error; tied incompatible cadences remain competing proposals. Suggested amount is the median, with observed minimum/maximum and support/coverage disclosed; no probability score is claimed. Missing normalized identity or insufficient consistent evidence yields no candidate. User adoption creates or updates a commitment and resolves overlap with existing commitments; no AI or automatic forecast adoption is required. A deterministic suggestion for variable spending is the median of the last three complete calendar months for the same account/category after excluding transfers, refunds linked under the chosen reporting convention, and activity already assigned to commitments. Fewer than three complete months yields insufficient evidence, not zero. The user can instead enter an estimate and label its basis.

An accepted variable-spending amount is a monthly **rate basis**, not a monthly ceiling. Allocate it across all dates of that month by equal daily shares and largest-remainder rounding; project only dates at/after the starting boundary that remain hypothetical. The first partially elapsed day uses one full daily share as an explicit conservative assumption, not a hidden intraday estimate. Stable variable occurrences are `(assumption_id, account, category, local_date)` with separate versions. Known post-boundary actual/pending allocations consume only the corresponding day’s estimate, clamped at zero; excess is actual variance and never suppresses later days. Pre-boundary actuals already in the starting balance are not charged again and do not reduce future-day rates. Thus spending above the historical median on day 10 does not imply no spending for the rest of the month. Matching date/account/category follows the saved assumption definition; incomplete classification creates an overlap warning requiring resolution rather than an automatic match. This is a rolling-rate forecast, not a budget. Assumptions must identify category/account, date basis, and exclusion sets so two estimates or a commitment and an estimate cannot cover the same activity. Rule adoption rejects overlapping active coverage; source reclassification can make an existing run need a new comparison, but cannot rewrite it. Scenario values are owner-supplied or explicitly adopted observed ranges, not statistical confidence intervals.

Scenarios are coherent household assumption sets, not simultaneous worst/best bounds for every account. Base uses nominal values. The external-cash-flow downside uses higher external outflows, lower external inflows, earliest allowed external outflow dates, and latest allowed external inflow dates; upside reverses those choices. Pure internal transfers retain nominal amount and dates in all three unless the owner explicitly overrides one shared transfer variable. Derived card-payment amounts are recalculated from each scenario’s purchase/statement assumptions. A single shared amount and ordered settlement schedule generates both legs; allowed lag and amount constraints are validated before execution. Thus one account may improve in a household downside scenario. Labels and per-account results must disclose this rather than call the scenarios mathematical lower/upper bounds. Market values and FX rates stay constant at the saved basis unless the owner supplies a named alternative assumption. No random simulation or implied probability is included in the MVP.

Each result reports daily balances, minimum projected balance/date, coverage, unresolved matches, omitted/unknown accounts, starting-position uncertainty, and assumptions. Saved forecast-versus-actual comparison uses the original saved output and maps actuals to its account/date/occurrence basis; later model improvements cannot rewrite prediction history. Time passing never invokes recognition.

## 10. Commands, queries, and local clients

### Versioned contract

Use one documented JSON message schema, Rust boundary DTOs and golden contract vectors, carried over local XPC and the private C ABI. The Swift host translates transport/authentication only and does not implement financial rules. Amounts and sequence values are strings, not lossy JSON numbers. Binary evidence uses bounded chunk-transfer calls. Major protocol mismatch refuses commands; minor additions are optional fields. Unknown financial command/event semantics are errors, never skipped. The MVP MCP transport is a local stdio bridge wrapping the same operations and redacted responses, not SQL or arbitrary filesystem access.

Every request separates stable `CommandBody` from live `AuthorizationEnvelope`. `CommandBody` contains protocol version, dataset ID, command UUID, expected commit head, operation kind and arguments; its RFC 8785 digest excludes capability/session/preview-token bytes. `AuthorizationEnvelope` contains current authenticated session, capability and preview/approval evidence and is never serialized into authoritative history. Adoption records attributed actor, authority/grant identity and decision metadata, not bearer secrets. A preview binds the stable command digest; identical retry after reconnect uses the original body and new authorization. The original expected head remains part of the body on retry; same-ID lookup occurs before stale-head rejection. A revised preview after a genuinely uncommitted stale command uses a new command identity. Owner-initiated mutations affecting financial meaning require a preview token bound to the exact payload, expected head, effects, warnings, and approval scope. Automated adoption instead requires an owner-approved standing rule grant bound to exact rule/version, operation kinds, accounts, conditions, and revocation state. Only the internal rule evaluator may exercise it. It generates and records the same validated effects/preview digest without pretending the owner approved each event; a rule change needs a new grant. Uncovered or conflicting cases return proposals for owner review. A changed head requires refreshing the preview in this conservative release, even if an optimization could prove no conflict. Commands serialize after admission. Only confirmed predispatch cancellation or confirmed transaction rollback proves no domain change. Once COMMIT may have been submitted, cancellation/lock returns pending or result_unknown until settlement; it cannot promise rollback. A completed commit cannot be undone by cancellation.

Validation order: authenticate and authorize; check protocol and dataset; return any prior result for the same command ID/digest; check expected head; resolve references and policies; verify allocations and accounting; verify preview/approval; commit. Reusing an ID with another digest is an error. Command result, authoritative history, journal rows, and invalidations commit together. A lost response is resolved through `GetCommandResult` before creating a new command identity. Status is one of committed, pending, result_unknown, or definitely_not_committed. A missing result row is not a negative result while an admitted command is in flight: consult admission state or wait behind writer completion. After restart, complete recovery/audit before returning definitely_not_committed. Only that definitive status permits a new attempt with a new identity; an identical retry may safely retain the original identity. Result retrieval requires the original authorized scope or fresh owner authority; knowing a command UUID cannot reveal its result to another client.

| Command family | Contract |
|---|---|
| `PublishImport` | Publish a verified staged batch and receipt/checkpoint. No recognition. |
| `AdoptInterpretation`, `SetOrganization`, `SetReviewDisposition` | Record explicit meaning/precedence/provenance; distinguish reporting-only edits from accounting changes. |
| `Recognize`, `CorrectRecognition`, `ReplaceAccountingSegment` | Exact previewed consequences; enforce recognition ownership and opening/correction rules. |
| `AssociateLegs` | Quantified lifecycle/transfer/payroll/duplicate association; reject overlap or include required corrections atomically. |
| `EvaluateReconciliation`, `ConfirmReconciliation` | Evaluate pinned predicate; confirmation rechecks dependency digest and records exact scope. |
| `SetCommitment`, `SetOccurrenceMatch`, `SaveForecast` | Planning-only durable changes; cannot append accounting postings. |
| `Export`, `Backup`, `Verify`, `Rebuild`, `Migrate` | Privileged maintenance operations with explicit destination, coherent basis, and recovery state. |
| `QueryPosition`, `QueryHistory`, `Explain`, `QueryReview`, `RunForecast` | Read-only outputs with basis/coverage/freshness; running a forecast is transient until explicitly saved. |

Stable error classes are unauthorized, locked, unsupported_version, stale_basis, invalid_reference, duplicate_recognition, allocation_conflict, unbalanced, precision_or_overflow, incomplete_basis, integrity_failure, storage_failure, canceled, and result_unknown. Errors identify affected scope and safe next action without exposing secrets. Successful queries identify processed commit and healthy/degraded/unavailable state. An older projection can be returned only as explicitly historical; it cannot satisfy a request for the current head.

### Authorization and process trust

`currentsd` is the only normal database/key owner. The official Mac app, CLI, importer, and MCP bridge have distinct designated signing identities; both ends enforce expected code-signing requirements and the same effective OS user. Authentication is not authorization: daemon-issued in-memory capabilities bind dataset, client, query fields/account scopes, permitted command kinds, expiry, session, and dataset instance identity. Actor identity comes from the authenticated grant, never a caller field. Preview approvals are one-use, expire after five minutes, and bind the same session and command UUID. Authorization is checked again when queued work executes; revoked grants fail even if previously admitted. Lock/revoke disconnects sessions and invalidates capabilities. No reusable capability goes in command-line arguments, URLs, logs, or exported history. Restricted account/field scopes apply to aggregates, explanations, errors, and counts as well as primary rows; an excluded account cannot leak through a total.

The Mac UI and interactive CLI request owner approval for mutation previews. The CLI invokes a bundled signed authorization helper that displays the exact preview and uses macOS LocalAuthentication device-owner authentication. Its one-use response binds a daemon challenge, command digest, session, and dataset instance. The daemon accepts it only from that mutually authenticated helper, never from a CLI flag or claimed actor. The Mac application need not be running; unattended CLI mutations are unavailable unless an existing explicit rule grant covers them. The MCP bridge defaults to owner-selected, redacted read scope and proposal submission only. It cannot approve its own proposal, read raw evidence/credentials, export a dataset, change scopes, or perform destructive maintenance. Raw financial read access is itself a privacy grant, not harmless merely because it is read-only. A signed broker does not make an external agent trustworthy.

The domain engine does not expose a shell, SQL executor, plugin loader, or arbitrary-path reader. Source workers receive only their connector credentials and ingestion scope, not dataset keys. The owner process never interprets a source string as a command. Local signing/permissions protect ordinary boundaries, not a compromised user account, root, debugger, malicious signed update, or invasive malware. Those limitations are explicit in section 12. The unsigned development service accepts synthetic datasets only and refuses production profiles. This is not a restriction on an owner explicitly decrypting a portable archive with an independent reader.

### Native interaction

The Mac app uses native navigation, tables, menus, keyboard access, selection, accessibility labels, document import/export, and inspectable detail. Required journeys are position-to-evidence explanation; transaction review and suspicious flagging; organization/split correction; reconciliation with exceptions; holdings/valuation inspection; and commitment/forecast inspection. Amount, source basis, coverage, freshness, and conflict cannot be separated into an optional hidden debug view.

All durable changes use the same preview and command results as the CLI. Repeated clicks reuse a command ID. A stale preview refreshes. Cancel writes no financial decision. Undo creates a compensating decision. Offline/locked/rebuilding states are explicit, and native client restoration cannot replay an old mutation as a new command. Pixel layout and window geometry are implementation details, not alternative financial semantics.

## 11. Storage, recovery, and lifecycle

### Transactional state and integrity

Production datasets live under a private application-support directory outside repositories, cloud-synced folders, build trees, and temporary directories. Directories are owner-only and files owner-readable/writable; path checks reject symlink escapes. Production dataset and archive v1 use a fixed documented SQLCipher 4 profile: 4096-byte pages, page HMAC enabled with SHA-512, encrypted header (no plaintext header), and raw 256-bit key input with SQLCipher-managed random salt/IVs. No passphrase mode or guessed compatibility fallback is accepted. The file-type/API profile selects these public settings before decryption; the encrypted manifest must agree afterward. A wrong key, mismatched profile, authentication failure, or unsupported format fails closed. Versioned readers must explicitly select a documented supported profile, never try weaker parameters until a file opens.

A dataset is one SQLCipher database containing authoritative records, evidence chunks, commit history, derived projections, and staging. WAL is enabled; disk temporary stores are disabled. SQL foreign keys and engine checks are mandatory. Credentials, raw encryption keys, and client bearer capabilities are never domain fields.

Committed evidence/domain records are append-only through the supported engine. Database permission separation is an access control, not proof against a privileged attacker. Each commit contains the previous commit digest and a SHA-256 digest of its ordered canonical records. JSON uses RFC 8785 canonicalization, with amounts, sequence counters, and precision-sensitive numbers as strings; raw evidence bytes retain their separate digests. This detects accidental corruption and disagreement with independent saved checkpoints, not malicious rewriting of the database and all its checkpoints.

The journal updates in the same transaction as a decision. Secondary indexes/reports may rebuild asynchronously; they advertise their processed head. A query requiring current semantics waits or returns unavailable, never a stale value labeled current. Rebuild writes a shadow projection, checks ordered journal/domain hashes against full replay, and switches the active projection atomically. It never overwrites authoritative history.

Snapshots are Currents-owned disposable encrypted acceleration records, not an assumed native doubleentry snapshot/import API. Until a prefix-restoration path is proven, snapshot acceleration may cover Currents derived state only and the native ledger is fully replayed. Correctness cannot depend on accelerating native restore. Snapshots are containing dataset identity, through-commit/head digest, snapshot/projector/schema versions, canonical replay-state bytes, and state hash; source-dependent views also pin their full read basis. Create one after each 10,000 committed records, or on clean close when at least 1,000 records follow the last snapshot. Only a snapshot produced from a verified replay state and matching its recorded history prefix can seed replay; incompatible, missing, or corrupt snapshots are discarded and full replay is used. Missing/corrupt authoritative history still fails rather than being hidden by a valid snapshot. Restore and upgrade always perform full replay, and an unlocked monthly verification compares full replay to snapshot-plus-tail state. A mismatch marks the projection untrusted and rebuilds from authority; it never chooses whichever hash is more convenient. Snapshots need not be included in backups.

Startup checks database/page integrity, schema compatibility, commit-chain continuity, referential integrity, active-segment/recognition ownership, and journal checkpoints. A failure makes financial commands unavailable and marks affected reads untrusted. Source-stale/partial, locked, projection-lagging, integrity-failed, migration-required, and recovery-in-progress are separate health states. Source staleness alone does not invalidate intact local history. No “best effort” skipping unknown records to produce apparently healthy totals. Recovery can inspect raw evidence in an isolated read-only mode with the failure attached.

### Keys and locking

Each dataset has a random 256-bit data-encryption key in the macOS Keychain, restricted to the production owner process and unlocked only after owner authentication. Connector secrets are stored separately with their required identities/scopes. Neither secrets nor database keys are passed through CLI arguments or environment variables. FileVault is recommended as defense in depth, not a substitute for dataset encryption.

The dataset locks on OS session lock, explicit lock, or 15 minutes of client inactivity. Lock first stops admission and revokes capabilities, requests cancellation, then drains/resolves the writer commit boundary and awaits all connection shutdown before reporting fully locked. A racing command remains pending/result_unknown until resolution, never assumed canceled. Clear key/session material as far as supported after closure. Scheduled acquisition cannot silently unlock it; it resumes after an owner unlock. This chooses visible delayed freshness over unattended access to decrypted financial history. No plaintext durable cache, crash upload, or content-rich log is permitted. Spotlight indexing, automatic Quick Look financial previews, financial window-restoration payloads, and clipboard copying are disabled by default; explicit owner copy/export is a disclosure action. Memory erasure cannot guarantee protection from swap, crash dumps, privileged debugging, or an already compromised machine.

A separate random 256-bit recovery key encrypts backups and full exports. The owner saves it outside the computer and demonstrates a restore before live acquisition is enabled. For automatic local backups, its device copy may be stored in the owner process's protected Keychain after explicit setup consent. No vendor escrow, server reset, or recoverable password substitute exists. Losing all usable key copies loses access; this must be stated during setup. Key rotation uses a new random key and the verified generation-switch protocol below; it never claims a filesystem change and a Keychain deletion are one atomic operation. Recovery-key rotation creates a new archive generation with a new key ID; the owner retains older keys until choosing what to do with older archives. Rotation cannot revoke a copied old archive/key pair. Restore generates a fresh local dataset key. Ingress-key rotation creates a new pairing epoch and one-time verified key exchange; normal rotation waits for queued-batch acknowledgment. Immediate revocation rejects all old-epoch bundles, and any surviving phone evidence must be repackaged under the new pairing with original capture metadata intact.

### Portable archive and backup

Full backup/restore has separate streaming limits: 64 GiB encrypted archive, 10 million logical records, and 1 MiB chunks by default, with destination-space preflight and an explicit owner override for larger validated datasets. It is not subject to the 100 MiB ordinary-evidence limit. Exceeding a quota fails before activation and leaves the source intact.

The portable format is a **single SQLCipher archive database** encrypted under the recovery key, with a documented simple interchange schema: canonical manifest, ordered JSON records, and evidence chunks keyed by digest. It is not a copy of opaque ORM objects. The manifest records format/cipher parameters, dataset identity, commit cutoff, semantic versions, counts, per-record/blob digests, journal/domain hashes, and included coverage. All retained authoritative records, complete source evidence, organization, claims, commitments, saved forecasts, and their dependencies are included. The archive includes versioned declarative policy definitions and the unit/calendar/reference data actually used, not merely labels naming unavailable versions. Public compatible readers implement the specified old semantics; archive data cannot install executable readers. Derived caches are optional and never substitute for authority. Credentials, capabilities, and device unlock keys are excluded.

The transfer variant uses a dedicated paired-device ingress key and contains only evidence/capture metadata, not dataset decisions or recovery material. Its manifest identifies that narrower kind; it cannot be restored as a full dataset. Authentication proves possession of the pairing key, not that a source institution attested the contents. Separate phone capture and Mac receipt times remain intact.

Export reads one pinned SQLCipher snapshot, streams records into a new encrypted archive, verifies counts/digests and replay, flushes it, and atomically renames the completed artifact. Incomplete `.partial` files are encrypted and never presented as completed backups. Archive readers open read-only with defensive/query-only settings, disable extension loading and trusted schema, accept only the documented tables/indexes, and reject triggers, views, virtual tables, unexpected SQL objects, oversized fields, and malformed relations. Archive contents never supply executable migration or policy code. Do not use SQLite's ordinary online-backup API with SQLCipher. Do not copy a live database file without its transaction state. Implementation must test the selected encrypted logical-export path rather than assume ordinary SQLite utilities preserve security.

The documented headless verifier decrypts, checks the entire manifest/reference closure, and replays without the Mac UI, network, institution account, or proprietary hosted service. An explicit plaintext JSONL/CSV export is a separate owner-approved disclosure operation with destination and warning; CSV alone is not full fidelity.

While unlocked, a changed dataset is backed up when 24 hours have elapsed since its last successful backup; unlocking also checks whether one is due. With no changes, retain the previous verified generation. A backup is mandatory before migration or non-erasing destructive maintenance. Deliberate whole-dataset destruction does not create a new retained copy unless the owner explicitly asks for one. If the owner declines protected storage of the recovery key, backup requires entering it through the secure local backup interface; the app requests that action when due and marks protection degraded rather than pretending unattended backup works. Default retention is all successful generations; no automatic pruning or undeclared cloud upload. Setup requires an owner-chosen independent backup destination and an offline recovery-key location. A local same-disk backup alone does not pass device-loss recovery. Backup status records cutoff, age, destination availability, last verified restore, and failure. A missing destination, failed backup, or changed dataset more than 24 hours beyond its backup cutoff immediately marks protection degraded without erasing or freezing access to existing records. Storage exhaustion stops new commits safely.

Restore always creates a new staging path. Validate archive/cipher format, page integrity, references, order, hashes, replay, and saved dependency closure before activation. The restored dataset preserves its identity/history but gets a new local instance identity; credentials, pairings, and grants are not reactivated automatically. The local owner registry rejects two writable active copies of the same dataset. Cross-device writable clones are unsupported; no global enforcement or automatic merge is claimed. An older backup is labeled rolled back relative to any retained independent checkpoint. Later histories are not automatically merged or overwritten.

### Crash-safe generation activation

A dataset has an owner-only registry with a small `CURRENT` marker naming a random generation ID and nonsecret key ID; each generation has its own directory and database/WAL/SHM files. The registry never contains financial fields or key bytes. Restore/migration/rotation acquires the exclusive owner lock, closes and awaits all readers/writers, verifies a new encrypted generation offline, and stores any new key in the protected key store **before** activation. Flush the verified new database and every required sidecar, then its generation directory, before publishing the marker. Write/flush the new marker in the same directory, atomically rename it, and flush that directory using the platform durability primitive. Do not rename an open SQLite database independently of its sidecars.

After restart, load only the marker's generation/key pair, validate format, instance identity and full replay, then permit writes. If verification fails, remain recovery-required; offer the retained prior verified generation without automatically mixing histories. Retain the previous generation and its key until the new one reopens successfully and the required backup is verified. A crash before marker activation leaves the old generation selected; a crash after activation leaves the new one selected and both keys available. Key retirement is a later separately recorded operation. Orphan staged generations are inspectable and removable only under the retention/deletion contract. This protocol is exercised with kill/I/O faults at every boundary; filesystem/power-loss claims are limited to qualified platforms.

Portable archive creation uses a fresh destination in rollback-journal mode, completes and verifies the logical export, explicitly closes all connections, verifies no required WAL state remains outside the archive, flushes the completed file, then performs a same-filesystem no-clobber rename and flushes the destination directory. Copy only the completed archive into an isolated empty directory and reopen it in a fresh process; if it cannot, export has not succeeded. The active dataset's WAL mode is unchanged. Mobile encrypted bundles and acknowledgments follow this same self-contained-finalization rule.

### Migration, retention, and deletion

A migration requires a verified current backup, exclusive owner access, and an offline staged copy. Original serialized authoritative events remain available; deterministic version readers/upcasters preserve their recorded meaning. Verify counts, references, canonical financial/domain hashes, and representative saved queries before atomically replacing the active store. A failed migration leaves the prior compatible store active or safely locked. An older application refuses a newer incompatible store rather than downgrading it.

Committed evidence, decisions, and saved forecast runs are retained indefinitely by default. Uncommitted failed imports and transient forecasts may be discarded after seven days; verified duplicates may share content, not lose receipt history. Disconnecting an institution deletes its credentials and stops fetching, but preserves accumulated evidence and decisions. No silent data deletion follows provider disconnection.

Routine correction and undo never erase. Selective destruction of committed evidence is **not supported by this preservation contract**; supporting a deliberately redacted history would require an explicit constitutional exception and new design, not an undocumented maintenance command. Whole-dataset deletion is a distinct owner-controlled operation that enumerates local copies, known archives, keys, and inaccessible backups, requires fresh confirmation, and states the consequences. Deleting a local key cannot promise remote-copy deletion or physical SSD erasure. The product must never claim deletion succeeded on an unreachable destination.

## 12. Threat model and failure behavior

Assets are source evidence, account identity, interpretations, financial history, credentials, encryption/recovery keys, saved forecasts, and accurate user understanding. Trust boundaries separate institutions/providers, source parsers, the mobile satellite, owner process, local clients/agents, OS/key stores, backups, and the public repository.

| Threat or failure | Control and visible behavior | Residual limit |
|---|---|---|
| Accidental public data/secret exposure | Private paths outside checkout; synthetic-only fixtures; allowlisted diagnostics; secret/data scans before publication. Logs contain operation/status/counts, not payloads, merchant names, balances, raw errors, or account IDs. | Scans are not a proof. Owner review of artifacts remains necessary. |
| Lost locked device or copied storage | Application-encrypted dataset/archive; separate protected keys; OS disk protection; owner unlock. | An unlocked or compromised machine can disclose live data. |

| Disk-full/crash/uncertain response | Atomic commit and command-result record, encrypted staging, idempotent retry/status lookup. | Storage failure can delay new work; prior state remains readable if intact. |
| Corrupt/unknown history or projection | Integrity checks and deterministic replay; no skipping; untrusted/unavailable status; shadow rebuild. | Hashes without an independent trusted checkpoint cannot prove non-tampering. |
| Malicious/obsolete dependency or update | Pinned reviewed dependencies, signed production releases, no runtime downloaded code, software bill of materials and compatibility checks. | Signing identifies a publisher, not correctness. Updates do not auto-migrate unverified data. |
| Unauthorized outbound disclosure | No telemetry, remote AI, cloud sync, or automatic diagnostic upload; owner chooses every new data recipient. | Explicit exports and OS sharing may create copies Currents cannot later erase. |

A signed CLI can be launched by an agent. Therefore CLI possession never substitutes for fresh owner intent: production write approval is issued by the trusted native approval surface or the signed LocalAuthentication helper described in section 10, not an automatic “yes” flag. The mobile ingress key grants only ingestion from that pairing, never reads or mutations of the record.

Failure states persist beyond a transient notification. A partially successful import names completed and failed intervals. Unknown command outcome is queried before resubmission. Revoked authorization requires re-consent. New source evidence can make a previous claim need review; it cannot silently “repair” the journal. Recovery/export failures preserve the source and do not advertise a completed artifact.

## 16. Rust integration, dependency ownership, and portability

### Frozen accounting adapter

`currents-domain` owns evidence, economic identities, decisions, recognition ownership, reconciliation and durable meaning. `currents-accounting` is the only crate permitted to call doubleentry. Its public output is a frozen `AccountingBatchV1`, not raw SQL, a callback, a native mutable store or an unvalidated posting escape hatch. The batch records ordered exact native commands, stable keys, account/unit references, document binding, native semantic version and required preconditions. The prebinding decision hash includes the native instruction bodies but excludes its own digest, generated Document hash and outer native-head/commit/result fields. Populate the native Document with that hash only afterward. Metadata-only native operations lacking Document support are bound by the ordered operation manifest in the outer domain commit. Native memos are disabled in v1; text stays in domain history, avoiding hidden random memo salts during replay. Imports, labels and forecasts may create domain commits without a native ledger commit.

For domain commit C, persist `native_head_after(C)` and canonical native result/checkpoint, or the unchanged prior head when there is no ledger effect. A query pinned at C uses that mapped native head, never assumes domain and native sequence numbers coincide. An event's decision digest is computed from its canonical frozen payload before native execution; a native Document binds that digest. The outer domain commit digest subsequently includes the resulting native head and event digests. This ordering avoids a circular hash definition. Receipt/decision IDs and expected results are allocated once and recorded; replay never regenerates UUIDs or timestamps.

The tested encryption candidate is SQLx 0.9.0 with the same `libsqlite3-sys` 0.37.0 instance and its `bundled-sqlcipher` feature (bundled SQLCipher 4.10.0, SQLite 3.50.4). SQLx's tagged tests demonstrate this feature combination; Currents' production composition is not yet qualified. Cargo feature/tree and linked-symbol checks must prove one SQLite implementation, not parallel stock and encrypted builds. A second narrowly reviewed seam supplies secure connection initialization before native schema access: every pool connection receives the key/profile before any reads, with no fallback. SQLx statement logging and debug display of connection options are disabled because key pragmas can enter formatted SQL. Key material never passes through URLs, environment variables or diagnostic arguments. Close/lock/shutdown explicitly await every pool/connection close; lifecycle tests cover the SQLCipher shutdown race reported upstream. Encryption/key-init changes are tracked separately from the proven transaction-composition patch.

The native calendar has one never-sealed period from `0001-01-01` through `9999-12-31`, the supported recognition date range; source dates outside it remain evidence but cannot be recognized in v1. Register native account windows and unit declarations at that floor, with immutable opaque internal account paths. Actual account opening/closure, names, unit availability and source dates are domain facts validated independently. This prevents the native append-only period calendar, immutable `open_from` and effective-date guards from blocking legitimate older evidence/backfill. Do not use native account-close changes, period seals or cosmetic path renames for domain lifecycle.

The native ledger policy is fixed from the same date floor with no maximum value-date drift; domain policy versions enforce changing financial rules without retroactively mutating native policy. Recognition requires a recorded `bookkeeping_date`: use the known institutional posting date, otherwise a known effective date under a disclosed fallback policy, otherwise require the owner to supply it. Native booking date is that bookkeeping date; native value date is the known effective civil date or bookkeeping date as an explicitly mechanical placeholder. Nullable original economic/posting dates remain nullable. Timestamp-to-civil-date conversion freezes the source timezone/offset policy and preserves original precision. Domain historical/reconciliation queries use meaningful domain dates, not placeholder native value-date totals. Every reversal supplies both the original native booking date and explicit original value date; never use the convenience reversal helper's default that substitutes booking date for value date.

Native `Op::Batch` supports entries/clearings/resets, not arbitrary declarations. It also limits one batch to 1,000 operations, each entry to 1,024 postings/16 Documents, and a canonical leaf to 65,535 bytes; preview validates these before acceptance. Account/unit declarations therefore use their own atomic metadata-only domain commits with their own command IDs and native-head mapping before recognition preview. They create no financial movement. A new security workflow predeclares metadata, refreshes the expected head, then previews/commits all known quantity/cash entries together. Failed recognition can leave harmless visible catalog declarations, not partial monetary effects. Never rely on a new native mixed-operation batch or smuggle declarations into raw SQL.

The storage adapter initializes native metadata before adding Currents tables, preserves the foreign-schema guard, namespaces Currents schema objects, and attests expected tables/indexes/triggers/migration hashes. The composition hook is private trusted code. It may write only named Currents tables through reviewed SQL; it may not change native tables, transaction control, schema, pragmas or connection state. Library upgrades revalidate this assumption against upstream source. No client, importer, plugin or deserialized input can provide a callback or SQL fragment.

Atomic correction/backfill may exceed one native batch. The private composition seam must therefore be extended and qualified to apply an ordered list of native operations/batches through the unchanged validator/persistence functions on **one shared transaction**, with each later operation reading the preceding uncommitted state. No intermediate COMMIT is allowed. This is a new unproven seam extension beyond the spike. Native batches retain their limits; a Currents atomic closure is capped at 20,000 native operations and 64 MiB canonical frozen instruction bytes. Larger closures fail visibly with source unchanged and require an explicit design/limit revision, never silent partial correction. Large previews reference a staged encrypted closure manifest/digest rather than exceeding the 1 MiB request limit. Confirmed cancellation before COMMIT submission rolls the entire closure back; a race at COMMIT follows the uncertain-outcome state machine. Progress is nonauthoritative. Tests include 1,200-operation correction, same-command retry, failure/kill in the final chunk, matching sequential native replay, and no current read observing an intermediate head.

Within the owner writer transaction: resolve same-ID retry; verify expected head and grants; validate references/recognition/allocations; record evidence/decision and derived invalidations; validate/persist native frozen batch via the seam; capture native head; record command result and domain commit; COMMIT. A confirmed validation failure before COMMIT rolls back both sides. A known COMMIT rejection followed by confirmed rollback also leaves neither side committed. COMMIT I/O or connection failure can be outcome-unknown even without a transport failure: preserve doubleentry/SQLx uncertainty classification, stop further writes on that connection, reopen and audit, then resolve the command-result/digest and complete native/domain correspondence before retry. Never report a rollback merely because COMMIT returned an error. No side effect occurs outside this transaction except already encrypted staging and postcommit notifications. If the transport/host loses the result after dispatch, outcome is unknown until status lookup or identical retry; never create a new ID to guess.

Each projection build records its semantic version and source prefix. Full replay reconstructs both Currents state and native canonical history in a new destination. Verify native audit, canonical leaf/head equality, ordered posting/domain hashes and command identity maps; equal final balances are insufficient. A stale/failed/divergent native projection cannot answer a current query. Startup full verification is the conservative initial policy; any incremental optimization requires equivalence tests and still validates authoritative prefix continuity.

### Precision, investment basis and FX

Wire values use section 5's exact representation. There is exactly one `SqlStore<Sqlite,18>`: doubleentry has a compile-time store scale, not arbitrary scale per posting. The adapter computes `coefficient × 10^(18-scale)` exactly, rejects overflow and `i128::MIN`, and enforces each declared currency/security exponent (0..18). Consequently the journal has a narrower whole-unit range than an unscaled i128 wire value; preview rejects an out-of-range amount before commit while evidence remains preserved. Unit exponents are immutable in v1; a changed source precision needs explicit unit mapping/migration, never reinterpretation of old values. USD monetary postings use exponent 2, securities their declared quantity precision. Every balance, partial sum and rescaling is checked. Each domain unit maps to a permanent collision-checked native code of 1–16 uppercase ASCII letters/digits; store the mapping explicitly, never use or truncate a UUID/ticker as native identity.

Analytical lot calculations may retain subcent values in domain analytical records, but native USD carrying-cost disposal is explicitly quantized to cents with half-to-even rounding and recorded remainder. The final disposal consumes the exact remaining cent balance. A cost allocation is not a hidden rounding plug for an inconsistent transaction. The USD8 spike is an analytical test convention, not permission to change production USD settlement precision. Larger-precision analysis must use an explicitly named analytical unit and cannot appear as cash. Multiplication/division uses checked widened arithmetic from a vetted numeric crate where i128 intermediate range is insufficient, then enforces the public range. No binary float enters authoritative or saved analytical calculations.

Baseline known-basis disposal uses explicit selected acquisitions or deterministic FIFO within one account/security/monetary unit, selected by adopted acquisition effective date then stable acquisition ID. The candidate inventory includes unknown-basis opening cohorts and their known/unknown acquisition dates. FIFO is unavailable as a complete known-basis calculation if an unknown/undated cohort could precede the selected known acquisitions; that disposed portion stays unknown unless evidence resolves it. Explicit selected acquisitions require supported ownership/quantity and an attributed choice, not an automatic way to skip an inconvenient unknown cohort. The user must preview that choice; it is analytical cost attribution, not a tax-lot election. A security transfer preserves acquisition/basis lineage and never resets purchase date. Partial lots allocate exact remaining cost under the unit's recorded rounding policy, with final disposal consuming the exact residual. A reinvested dividend links income and acquisition. A split applies a rational quantity ratio and preserves aggregate carrying amount; fractional cash-in-lieu is a distinct event. Corporate actions without supported complete terms remain observed holdings and unresolved history, not guessed lots.

A sale with unknown or partially known basis follows section 8 disposal clearing and exposes unavailable/partial gain; never mix its unknown portion into a complete realized-gain total. Acquisition fees are capitalized into the adopted carrying basis. Disposal records gross proceeds against allocated basis and gross realized gain/loss, and posts selling fees once as a separate expense; cash received is gross proceeds minus those fees. Report gross gain separately from net realized result (gross gain minus selling fees), never subtracting the same fee twice. Lot selection includes only quantities available by the disposal's adopted economic/bookkeeping date, never future purchases. Corrections to acquisition cost, quantity, date, transfer or split revalidate dependent disposals and invalidate derived gain/valuation claims atomically; they cannot leave a stale known-basis result current. Conversion policy is disclosed. Source-reported realized gain may be shown as an assertion, not substituted for a missing reconstruction. Investment returns and tax reports remain outside initial scope.

FX recognition records source/destination units and amounts, quote direction (destination units per source unit), source/time, fee amounts and units, declared cash rounding, and residual explanation. Recompute destination amount at that quote before adoption; reject inconsistency beyond the explicit cash quantization, or preserve the amounts as an unresolved exchange without claiming a validated rate. Both currencies still balance through explicit exchange-control accounts; metadata alone does not prove conversion economics. Valuation FX rates are separate price observations with age and provenance. A missing or stale rate cannot produce an unlabeled current total. Independent Beancount/Ledger oracle fixtures check exact fractional quantities, known/unknown basis, fees, splits, transfers and FX; they are dev-only and not runtime dependencies.

### Persistent Rust/Swift boundary

`currents-ffi` exports a small versioned C ABI generated with cbindgen: create/close opaque service handles, submit bounded request bytes, obtain/copy/release owned response bytes, cancel before dispatch and resolve command status. Handles are non-reusable generation-tagged tokens with checked ownership, never caller-dereferenced Rust pointers. Every exported function returns a status; no Rust panic or Swift exception unwinds through C. `catch_unwind` converts recoverable panics to service-failed, invalidates the affected handle and requires reopening/audit; process abort/OOM/crash still produces an unknown outcome. The release build retains unwind containment rather than relying on `panic=abort` for recoverable protocol errors.

Swift calls through an actor, keeps Rust work off the main actor, enforces response limits/version/schema, and releases owned buffers exactly once. Cancellation after dispatch does not imply rollback. Every recoverable post-dispatch copy/decode/version/release failure is `result_unknown`; status lookup or identical retry proves whether one commit occurred. Destruction is idempotent and nonthrowing; cleanup must never hide a committed result behind a fatal assertion. Production work must combine this contract with persistent encrypted storage and repeat the memory-only spike's seven fault/retry cases against real durable writes.

Rust core and headless verification build on macOS arm64 and Linux x86_64. Primary signed UI distribution targets macOS arm64. Intel Mac support requires its own native CI/build/signing fixture and is not implied by cross-compilation. The implementation plan pins a tested Rust/MSRV/Xcode/macOS target and upgrades deliberately. A future single-owner server uses the same commands/replay, one writer and encrypted record, with host-specific key/approval adapters. It needs a separate deployment/security ADR; no sockets, remote credentials or cloud infrastructure are introduced merely for future compatibility.

## 17. Project quality and release contract

The workspace keeps crates private (`publish = false`) until separate crate-publication approval. It commits `Cargo.lock`, toolchain configuration, reproducible fixtures, schema/ABI vectors, dependency source/license inventory and build instructions. Native Apple scaffolding never becomes the only way to build/test the engine. Narrow established libraries handle storage, serialization, date/time, CLI, crypto/key integration, HTTP and diagnostics; Currents owns financial interpretation, authority and invariants. Add dependencies with one named purpose and minimal features, not a framework that duplicates the domain.

Pull requests must pass format, compiler warnings, selected strict Clippy lints, unit/integration/property tests, locked builds, MSRV, docs, protocol compatibility, privacy/secret checks and dependency/license policy. Unsafe code is forbidden in safe domain crates and isolated with documented safety invariants in FFI/platform wrappers; fuzz/sanitizer/Miri checks cover the boundaries where applicable. CI runs without private datasets or provider credentials; forked PRs cannot access release secrets or write permissions. Dependency advisories and nightly fuzz/fault runs create actionable failures with owned, expiring exceptions rather than silent global exclusions.

Every release has a reviewed changelog, conventional change categories, migration/backup/compatibility instructions, release notes, checksum manifest, SBOM and provenance. Build from an approved tag and tested commit with pinned Actions and minimal token permissions. Separate ordinary CI from signed/notarized macOS release jobs; signing material is supplied only by a separately approved secure release setup. Release candidates are installed, launched, upgraded and restored on clean supported machines. Do not publish crates, Homebrew changes, containers or automatic updates without explicit scope. An initial manual download/install flow is acceptable; if auto-update is later selected, signed-update verification and rollback/migration behavior need their own ADR and tests.

No release is called a usable household MVP until all S1–S12 journeys, full-picture scope, real-data protection gates and account-coverage decisions are satisfied. Earlier tags are clearly synthetic-only developer previews. The implementation plan must carry this distinction through milestones and issue acceptance criteria.
